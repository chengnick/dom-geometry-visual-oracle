# UI_Test — 分層 UI 測試練習場

以「薈柚 Huì Yòu」品牌手工皂靜態網站為受測對象，示範一套**分層的 UI 測試策略**，並在遇到業界標準工具的限制後，自行設計了更適合的替代方案。

核心敘事：**先用現成工具撞到痛點，再自己做一個更合適的工具解掉它，最後連自製工具本身都補上單元測試。**

---

## UI 測試的三個層次（別混為一談）

| 層次 | 問的問題 | 本專案的實作 | 工具 |
|---|---|---|---|
| **1. 功能性 E2E** | 點得到、走得通嗎？ | `tests/smoke.spec.js` | Playwright |
| **2. 視覺回歸** | 畫面長得跟基準一樣嗎？ | `tests/visual.spec.js` | Playwright `toHaveScreenshot()` |
| **3. 版面幾何驗證** | 元素的座標/尺寸/樣式跑掉了嗎？ | `ui_layout_checker/` | 自製工具（抓 DOM 幾何存 JSON） |

---

## Step 1 — 視覺回歸（用內建工具，並撞到它的極限）

`tests/visual.spec.js` 用 Playwright 內建的 `toHaveScreenshot()`，對首頁全頁 / Navbar / Hero / 商品區塊四個區塊截圖比對，跨 chromium + firefox + webkit 三個引擎，共 12 個測試。

**驗證過程**：
1. 12/12 通過，產生基準圖
2. 故意把 Hero 標題字級 56px→72px、顏色改紅 → 正確抓出 6 個失敗（3 引擎 × 2 個受影響快照），不受影響的 Navbar/商品區塊維持通過
3. 改回原樣 → 恢復 12/12

**撞到的痛點（正是 Step 2 的動機）**：
- **儲存成本高**：3 引擎 × 4 區塊的基準圖就達 **6.3 MB**，單張全頁截圖 1.3~1.5 MB。多頁面／多品牌下會線性爆炸。
- **容差難調**：全頁快照因 CSS 背景圖與字型渲染，需加 `maxDiffPixelRatio: 0.02` 才穩定；小區塊反而不需要。同一套容差不適用所有區塊。
- **只知道「哪裡不一樣」，不知道「為什麼」**：diff 圖只標紅像素，不會告訴你根因是字級變了還是元素被推移。

---

## Step 2 — 自製 `ui_layout_checker`（解掉 Step 1 的痛點）

**核心概念**：不存截圖、不比像素，改抓每個關鍵元素的 `boundingBox()`（x/y/width/height）+ 關鍵 computed style（字級/字重/顏色/背景色），存成結構化 JSON 當基準，下次重抓比對。

**檔案結構**：
- `config.js` — 選擇器清單、要抓的樣式屬性、容差公式參數
- `extract.js` — 共用抓取邏輯（boundingBox + computed style）
- `diff.js` — **純比對邏輯**（不開瀏覽器、不讀檔），方便被單元測試
- `capture.js` — 產生/更新基準 `baseline.json`
- `compare.js` — 比對並印出差異報告，有差異時 exit code 1（可接 CI）

**容差公式**（設計精華）：`max(絕對下限 2px, 相對百分比 1% × 元素自身基準尺寸)`
- 絕對下限吸收次像素渲染雜訊，小元素不誤報
- 相對百分比讓容差隨元素尺寸縮放，大區塊本來就有更多正常浮動

**成果對照**：

| | Step 1 截圖 | Step 2 JSON |
|---|---|---|
| 體積 | 6.3 MB | **2.6 KB**（小三個數量級） |
| 比什麼 | 像素 | 版面結構 + 樣式 |
| 對字型渲染差異 | 敏感、易誤報 | 不受影響 |
| 回報內容 | 一塊紅色像素 | 具體欄位：`fontSize 56px→72px`、`y 位移 19.2px` |

**驗證時挖到的邊界案例**：改動 Hero 後，除了標題本身，還連鎖抓到下游 3 個元素因版面被往下推的 y 位移。其中成分卡片位移 **19.21px vs 容差 18.89px**——只差 0.3px 決定「跑掉」還是「正常」。若容差用固定值就會漏抓，正是「容差設計是精華」的活實例。

---

## Step 3 — 為自製工具補單元測試（元一層的嚴謹）

「測試工具自己也要有測試。」`tests/diff.spec.js` 針對 `diff.js` 的兩個純函數 `geometryTolerance()` 與 `diffSelector()` 寫了 15 個單元測試，涵蓋容差公式邊界、found 狀態、幾何容差邊界、樣式差異。

**兩個刻意的設計決策**：
1. **為可測試性重構**：原本這些純函數藏在 `compare.js`（含 `launch browser` 副作用）裡。因為「要測它」的需求，把純邏輯抽到獨立的 `diff.js`——需求反過來逼出更乾淨的架構（純函數與副作用分離）。
2. **變異測試驗證**：把比對邏輯的 `>` 故意改成 `>=`，確認**正好只有那條邊界測試失敗**（14 過 1 敗），證明測試真的守得住邊界，不是橡皮圖章。

## 指令

```bash
npm install                 # 首次執行前（含 npx playwright install）

npm run test:unit           # Step 3：diff.js 純邏輯單元測試（不開瀏覽器，最快）
npm run test:visual         # Step 1：視覺回歸（三引擎截圖比對）
npm run layout:capture      # Step 2：建立/更新版面幾何基準（確認畫面正確後才執行）
npm run layout:compare      # Step 2：平常檢查版面有沒有跑掉

npx playwright test tests/smoke.spec.js   # 既有功能性 E2E（打線上網址）
npx playwright show-report                # 視覺化比對報告
```

> `layout:capture` 只是無條件把「當下畫面」存成新基準，不會判斷對錯。務必先肉眼／視覺回歸確認畫面正確，再 capture，否則會把壞掉的版面存成基準。

---

## 一句話總結（履歷用）

> 發現業界標準的截圖式視覺回歸在多頁面／多品牌下會遇到儲存爆炸與渲染誤報，於是設計了改比 DOM 結構化幾何資料的替代方案（體積小三個數量級、比結構不比像素），並為其比對核心補上單元測試與變異測試驗證。
